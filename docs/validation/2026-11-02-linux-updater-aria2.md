# Linux 单文件更新器与 aria2 下载回归

## 问题与修复

用户日志中的错误是 `aria2 下载预检失败：Head ... context deadline exceeded`：旧代码在启动引擎前强制执行最长 5 秒的 HEAD 请求，GitHub 或镜像响应较慢时直接回退 Go 下载器。这不等于 Linux 无法执行 aria2。已删除强制 HEAD 预检，让引擎直接下载；下载进度及落盘文件仍执行大小限制，更新文件仍按发布清单验证摘要。

本地对旧引擎真实下载还发现：开启 RPC 后，aria2 下载完成仍常驻，原逻辑却等待子进程退出，最终可能直到上下文取消才报失败。已通过 RPC 终态识别完成或错误，再回收引擎进程。实际小文件和 8 MiB 下载均通过，不再在完成后挂住。

旧锁确认直接读取 `consoleReader`，与后台统一输入线程竞争同一输入流，可能输入 Y 后等待不前。生产路径已统一到 `readConsoleLine`，并保存 EOF 状态，避免输入关闭后再次等待永远不会到来的数据。旧锁仍需要用户明确确认清理。

正式 Windows amd64、Linux amd64、macOS arm64 的客户端和服务端六个更新器均以 `-tags bundled_aria2` 构建，嵌入固定 SHA-256 的对应平台 aria2 1.36.0 可执行文件，不再要求用户单独下载和配对引擎。运行时释放到更新器所在文件系统上的进程私有目录，校验后授予 0700 权限，正常结束后清理。Release 不再提供独立 aria2c 文件或旧命名别名，只提供六个更新器；GPL 通知与对应源码继续随同版 Release 提供。发布前先下载并校验引擎，再构建六个二进制。

## 本地验证

- 固定 Linux 引擎 `--version` 正常执行，`file` 显示静态 ELF，SHA-256 与发布固定值一致。
- Go 完整测试、带内置引擎的完整测试、`go vet` 与带内置引擎的 `go test -race` 通过。
- 真实内置引擎测试覆盖 4096 字节、8 MiB、带空格路径、服务端拒绝 HEAD，下载字节与原始内容一致；自动释放摘要、权限和清理检查通过。
- `scripts/integration/updater_linux_e2e.py` 使用真实 Linux 服务端单文件二进制，在独立临时实例复现 0.2.67 → 0.2.73：仅放更新器、不放外置引擎，预先创建残留锁，依次输入两次 Y；在拒绝 HEAD 的本机 HTTP 来源下载清单和 8 MiB 更新包，文件摘要一致、VERSION 更新、原有世界文件保留、签名状态生成，且更新锁及进程私有引擎目录均已清理。未触发 Go 下载器回退。
- 六个平台/用途组合交叉编译通过，逐个验证包含对应平台完整引擎字节；Linux 二进制 `--help` 显示内置引擎说明。Windows/macOS 原生环境由对应 CI 运行同一真实引擎下载测试。
- 清单及工作流静态检查、工作流 shell 语法检查、Python 测试通过。正式发布工作流和更新器 CI 同步加入真实 Linux 更新事务验证。

## 范围

未登录用户的 Ubuntu 生产服务器，也未对其网络连通性、磁盘或文件系统状态作保证。网络来源失败仍按既有镜像切换与内置 Go 下载器回退策略处理。测试使用本机 HTTP 来源验证程序路径，无法证明用户所在地的 GitHub 或镜像始终可用。
