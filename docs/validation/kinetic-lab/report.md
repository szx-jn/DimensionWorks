# 应力网络基线实测报告

2026-11-04，仓库提交和运行环境见 [environment.json](environment.json)。探针及重现步骤见 [测试目录](../../../scripts/performance/kinetic-lab/README.md)，实施任务见 [6luna 交接文档](../../design/kinetic-network-implementation-handoff.md)。

## 结论和证据范围

确认存在四条可重复的放大路径：变化次数×网络成员数的广播、容量纯读扫描全部来源、跨网络配额样本的平方级访问、ME 输出口纯读引发整个服务重算。真实长轴网络变速还有成员移除/接入与传播开销。稳定轴链没有每 tick 重复账目计算，不能把全部机器 tick 开销称为应力求和。

实验运行真实 Forge 47.4.16、Create 6.0.8-291、RPM 0.4.17、Mek-Stress 0.3.20、Mekanism 10.4.16.80、AE2 15.4.10、Applied Create 1.1.5 及它们声明的依赖，使用官方映射。不是完整整合包，也没有玩家工厂存档；不能据此承诺完整整合包的 TPS 或全部附属兼容。

Maven sources 的 KineticNetwork 和 RotationPropagator 与 tag mc1.20.1-6.0.8 完全一致。KineticBlockEntity 只有 convertToAngular 的等价角速度表达式及注释差异，应力同步方法一致。运行 slim jar SHA256 已记录。

## 测量方法

账目夹具使用实际已加载方块实体，人工归入同一个网络，明确隔离广播和缓存成本；它不代表自然生成的传动拓扑。physical_* 夹具另建 128/512/1024 节点的实际轴链，断言成员全部连接。ME 夹具使用一个记忆驱动器、创能方块和 8/32/128 个零应力输出口，断言处于同一 AE 网；AE 频道设为 infinite 用于隔离 CPU 算法，不代表修改整合包玩法。

每场景预热一次，再测五次，额外记录 100 个稳定服务器 tick。计数只在测量窗口开启；JFR 同步记录。wall_ns 包含调度停顿；cpu_ns 是服务器线程 CPU 时间。计数探针本身有开销，所以毫秒是诊断基线，不是无探针生产性能。重复 JVM 的原始结果保留在 samples.csv、ticks.csv，聚合见 summary.json。

## 已确认的调用量

| 场景 | 输入 | 实际操作次数 | 解释 |
| --- | --- | --- | --- |
| 分散负载更新 | N=4096，U=100 | sync=100，成员更新409600 | 差量应力缓存没有消除广播 |
| 同样负载更新置于现有 batch | N=4096，U=100 | sync=1，成员更新4096 | 只证明事务内合并有价值，不证明任意延迟到 tick 末安全 |
| 等值失效后刷新 | N=4096，10次 | 重建10次，sync=10，成员更新40960 | 普通 invalidate 写入加载强制同步标志 |
| 缓存容量纯读 | S=512，100次 | 来源读取51200次 | 配额层绕过自然容量缓存的收益 |
| G个网络各读容量一次 | G=16/64 | 全局样本访问256/4096次 | G²访问路径由计数确认 |
| ME输出口各读生成转速一次 | P=128，加1驱动器 | snapshot=128，参与节点访问16512次 | P×(P+1)，纯读仍全服务重算 |
| 真实轴链变速 | N=128/512/1024 | 成员更新382/1534/3070次，sync=1 | 约3N，不能只继续合并sync就解决 |
| 真实轴链断源 | N=512/1024 | 成员更新512/1024次 | 实际组件遍历成本，部分工作不可消除 |

## 正确性及测试历史

两个模组现有单元测试 74+85=159 项通过。包括数学、接口及源码契约测试；源码契约不能替代运行证明。自建 GameTest 同时断言成员数、真实连接、ME 网连通以及差量应力与逐成员完整计算一致。

初次隔离构建有4项测试因相对路径读取缺少仓库文件失败，修正 test.workingDir 后全部通过。首次资源下载有3个瞬时失败，重试成功。探针初次编译引用 AllBlocks 间接要求编译期 Registrate，改为 Forge 注册表查询后通过。首轮大网络部分全部完成，ME场景因超过无控制器8频道上限而失败，调整实验频道变量后完整基准通过；不能把这些夹具或环境问题归因于应力算法。

首次成功轮复用了前次世界，其远处 ME 方块未被小模板清除。同步调用量场景仍可用于确认路径；稳定tick比较采用后续新世界轮，避免残留网污染。重现脚本明确要求每轮使用新世界。

## 解释和实施边界

目前最直接的收益来源是减少重复广播和重复配额/ME遍历。批处理不能推迟新增负载扣账，不能允许本应过载的后续机器继续加工；过载翻转、真实变速和未知附属兼容路径必须保留即时屏障。真实传动变速应进一步定位成员迁移与失效，再决定传播改造。

未覆盖完整第三方附属组合、真实加工阵列、反应堆完整结构负载、所有者共享额度的全部组合、长期重启/卸载循环和客户端图形。相关项目已经列入实施验收，不标记为测试通过。当前交付是可复现证据和实现规格，不是已完成优化的版本。

稳定窗口的“没有重建/广播”不等于没有任何 getActualStressOf 调用：异步安排的保存可通过 KineticPersistence.write 扫描物理贡献；变速刚结束时也可能有待处理刷新。应将窗口前段的收敛、保存调用与持续 network.calculateStress 重建分开看。测试回调内有大量刻意连续操作，日志中的 Can't keep up 不能直接视为正常工厂负载的测量。
