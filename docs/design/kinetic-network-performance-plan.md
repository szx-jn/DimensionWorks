# Create 应力网络性能改造方案

## 基线与证据边界

2026-11-04 源码审查。整合包清单固定 Create mc1.20.1-6.0.8；自研工程依赖 6.0.8-291 slim，Minecraft 1.20.1、Forge 47.4.16。上游源码已克隆至 `/workspace/Create-6.0.8`，tag `mc1.20.1-6.0.8`，提交 `1a1a9a2819b4f89f78caec41b55ed8cb222fa24b`。正式实验还须核对运行 jar 的哈希和实际加载 mixin，不能把源码版本标记当成二进制一致性证明。

本文件是实施方案，不是已经优化完成的报告。真实 Forge 服务器基准与测试世界已准备并运行，证据见 [实测报告](../validation/kinetic-lab/report.md)，具体实现任务见 [6luna 交接](kinetic-network-implementation-handoff.md)。没有当前玩家存档的 CPU 采样，也没有完整整合包兼容结果。当前容器没有可用图形桌面，未启动可见客户端。

## 已确认的放大路径

N 为一个动力网络成员数，S 为动力源数，U 为一次结算窗口内变化数，G 为已登记动力网络数，P 为 ME 服务参与节点数。以下是操作次数模型，不是实测耗时。

| 路径 | 源码证据 | 放大方式 |
| --- | --- | --- |
| Create 总账刷新 | `KineticNetwork.updateStress/updateCapacity/updateNetwork/sync` | 总账任一浮点值变化即遍历 N 个成员；U 次分散变化可触发 O(U×N) 成员更新 |
| 成员更新 | `KineticBlockEntity.updateFromNetwork` | 每次调用都 setChanged；只有过载翻转才 onSpeedChanged/sendData，不能误称每次都发包 |
| Mek 虚拟机器与反应堆输入 | `MachineKineticRegistry.sync`、`ReactorInputRegistry.sync` | 变化后立即 updateNetwork；增量求和并未消除全网同步 |
| 发电机桥接 | `MekanismGeneratorShaftMixin` | 普通轴每 tick 检查外部动力源；容量变化立即 updateCapacity；多个源可分别广播 |
| 容量配额 | `CreateCapacityRegistry.limitNaturalCapacity/ownerCapacities/rawCapacities/registerOwners` | 缓存自然容量后仍扫本网络 S 个源和全局所有者样本；一个样本变化标记其他所有网络，G 个网络刷新可产生近似 G² 级全局样本访问（每网所有者数量固定时） |
| ME 实时额度 | `MemoryGridService.snapshot`、`MEGearboxBlockEntityMixin.dimensionworks$refresh` | snapshot 未利用 gameTick 缓存，tick 首尾及调用方都可重新遍历 P 个参与节点并应用输出；若 P 个调用方各请求一次，达到 O(P²) |
| 缓存失效 | `KineticNetworkOptimizer.invalidate/onTopologyChanged/onMemberLoadedSilently` | 应力、容量、RPM 上限和保存快照一起失效；与计算交错的成员加载/变更会反复重建 |
| 强制同步 | `invalidate`、`finishLoadedNetworkRefresh` | 所有 invalidate 都写 PENDING_LOAD_REFRESHES，普通失效也可能在数值不变时触发一次全网同步 |
| 应力表红石 | `StressGaugeBlockEntityMixin` | 每次 updateFromNetwork 都通知邻居与比较器，即使最终红石输出不变 |
| 外部动力发现 | `ReactorPowerBridge.outputFor`、`GeneratorPowerBridge` | 查询生成速度/容量会检查附近方块；反应堆还可能查核心和输出端，重复查询叠加在每源计算上 |
| 持久化 | `KineticPersistence.write` | 同网络同 tick 复用快照已避免常见逐方块全扫，但账目变化仍使快照失效 |
| 旋转传播 | Create `RotationPropagator` | 新源递归传播；断源遍历再选源，期间成员发包及网络迁移。不能仅通过缓存应力总和消除 |

特别注意：`propagateMissingSource` 的 frontier 是 LinkedList，`remove(0)` 是常数时间，不能据此声称存在 ArrayList 队首搬移瓶颈。图传播重复访问量、递归深度和附属自定义连接开销必须单独测量。

## 总体设计与正确性约束

采用按网络维护的权威账本、按变化原因区分的版本、统一刷新调度器。基础应力系数、实际贡献、自然容量、配额后容量、物理持久化余额分别保存。真实结构变化、速度变化、所有者变化、额度变化、加载恢复分别递增对应版本，不能一律清空所有缓存。

机器开始加工前必须把新增负载计入权威账本并判定过载。任何减容或新增负载导致的过载必须立即对后续加工可见。不能只把全部 updateNetwork 推迟到 tick 末：已有附属读取成员 overStressed/getSpeed，延迟广播会允许同 tick 免费加工。第一阶段保留过载翻转、转速变化、网络迁移和必要兼容回调的同步屏障；普通数值变化可合并发布。第二阶段若引入成员按网络版本懒刷新，必须覆盖所有直接读成员字段/重写 updateFromNetwork 的附属，完成兼容审查再启用。

未知第三方直接修改公开 members/sources 的行为采用明确的兼容钩子或保守重建；不以每次读取全量校验抵消优化。不要强制加载区块。只保存物理成员账目；虚拟负载按实时输入重建。浮点校验采用确定性完整重建作对照；double 累加降低漂移但最终保持 Create float 比较边界，不引入会改变临界过载判定的任意 epsilon。

## 实施顺序

### P0：建立可重复证据

创建隔离实验实例与备份存档，记录 jar 哈希、配置、JDK、堆大小、世界坐标、场景种子。上游 Create 最小依赖实例和当前自研集成实例分开；完整整合包用于最终兼容验证。探针为开发专用，不进入正式 jar。使用 JFR/服务器 profiler，按线程查看服务端 CPU，排除客户端软件渲染和区块生成的干扰。

每网络每 tick 汇总 updateNetwork/updateStress/updateCapacity/sync 次数、访问成员数、缓存命中与按原因失效次数、ME snapshot 次数、配额扫描样本数、外部动力探测次数、setChanged、sendData、红石通知、传播节点访问和最大递归深度。低频输出聚合结果，禁止逐成员日志污染测量。

### P1：移除无意义重复工作

1. 应力表缓存最终输出信号，仅信号变化通知红石；加载、拆除和初次同步明确初始化语义。
2. ME snapshot 使用参与者版本、输入版本和输出配置版本。查询无变化时直接返回；输入同 tick 发生改变仍须立即失效，不能简单用 tick 相同就复用。节点移除/禁用即时撤销额度。图稳定时一次分配供全部读者复用。
3. 统一虚拟机器、反应堆输入、发电机、ME 输出的提交入口。先更新权威总账，再判断是否需要即时屏障，普通发布在 tick 末按网络身份去重。嵌套刷新使用待处理版本，避免回调递归；异常路径通过 finally 关闭事务，不依靠 tick 末清理泄漏维持正常语义。
4. PENDING_LOAD_REFRESHES 仅用于真正的恢复场景。普通失效使用独立标志，避免等值总账的强制广播。
5. 保持已有效的应力增量更新；容量重建避免上游扫描后再次计算全部来源贡献。缓存重建期间剪除成员不得清掉本轮已记录贡献后又把不完整账本标记为有效。

### P2：按所有者增量维护容量配额

维护 network→owner→自然容量、owner→总容量、owner→相关网络反向索引。源变化只调整所属桶的差值；自然容量不变的查询不再扫描 sources 或 SAMPLES。所有者进度变化只重算该所有者相关网络。共享桶是明确的全局依赖：共享容量变化可能确实影响全部受限所有者，必须保留这类广播，而非错误局部化。卸载、移除与服务器关闭主动清理索引；WeakHashMap 不应承担确定性业务清理责任。保持未加载容量的共享桶归属规则。

预期普通来源变化成本接近 O(1 + 受影响网络数)，替代每个读者重新汇总所有网络。

### P3：拓扑、RPM 与发现缓存

单成员添加/移除直接增减贡献；只有全网有效速度规则变化或未知修改需要全量重建。区块恢复按事务汇总未加载余额、最后同步一次。RPM 最低上限维护所有者计数与上限频数，处理最小值拥有者移除、无所有者成员继承规则、离线所有者及配置重载。

外部发电机/反应堆维护已加载接口和轴的绑定索引，结构变动、邻居变动、区块卸载失效；发电量保持每 tick 新鲜，不能缓存跨 tick 的动态输出。普通无外部源轴可缓存负结果，但邻居装上源必须立即失效。同 tick 复用核心结构和输出端枚举，不重复从各读取路径发现结构。

保存快照按账目版本复用并考虑物理/虚拟区分；不以保存行为触发网络刷新或临近区块加载。

### P4：谨慎改造 Create 传播与成员发布

先测传播热点，再决定是否用显式工作栈替代递归。必须保留轴/齿轮传动比、方向、转速冲突、源优先级、自定义 propagateRotationTo、破坏与重接的顺序语义。访问状态至少包含有效源与速度版本；简单 visited 节点集合可能错误跳过同一节点的新状态。

普通数值变化的全网广播合并后仍存在一次 O(N) 成本。进一步改为权威网络状态和按需刷新前，列出所有附属读取与通知契约。过载翻转可能确实要求通知全部成员，真实结构拆分也至少需要访问受影响组件，不承诺将这些事件变为 O(1)。

上游源码保持只读；需要修改上游时使用独立 fork 和固定 Release 资产。先通过现有自研模组的集中适配实现；不擅自添加清单依赖或直接修改第三方工作副本。

## 模组覆盖与边界

首要实施点：dimensionworks-rpm-limit、dimensionworks-mek-stress、dimensionworks-stress-gauge-alarm。洞穴工厂的机器 tick/配方加工应单独计量，不能仅因继承动力机器就归因于网络算法。create-culling 属于客户端渲染优化，不能作为服务端应力优化的收益。拓扑诊断是手动快照，分页排序成本应在打开 GUI 场景单独测。

清单中的第三方 Create 附属（包括 Applied Create、Connected、柴油发电等）并非全部源代码都已审查。最终验收须从实际加载列表收集其网络写入、速度回调、自定义连接与 mixin；锁定各自版本，逐个启用回归。不能据本次本仓库源码审查宣称所有附属无其他瓶颈。

## 实验矩阵与验收

- 网络规模：100、1000、5000、10000；单大网络与相同总节点数的多小网络。
- 拓扑：长链、分支、齿轮倍率、多动力源、合法环路与冲突；稳定运行、切速、断源、合并、拆分。
- 附属：虚拟负载批量接入与升级、动态发电、反应堆负载变化、ME 多输入输出、所有者/共享额度变化、应力表红石反馈。
- 生命周期：跨区块加载卸载、重登、自动保存、重启、移除最低 RPM 成员、离线所有者恢复。
- 边界：刚好不过载/刚好过载、浮点长期累积、相同 tick 先加工再增负载/先减容再加工、服务器停机清理。

每组预热后重复至少三次，记录 tick p50/p95/p99/最大值、目标线程 CPU、分配率、GC、方法调用次数，记录硬件与总加载方块实体。不能将不同机器的绝对毫秒直接对比。

验收目标：无输入变化不重建账本和配额；普通同 tick 数值变化每网至多一次合并发布，真实过载/转速/拓扑屏障例外并单独计数；ME 无版本变化不重复扫描；无信号变化不通知红石；无新强制区块加载；与基线完整计算账目和实际产量一致。对指定规模单独设定服务器 tick 预算（20 TPS 总预算 50ms，但并非全部分配给应力）。若瓶颈转移到真实机器加工，单独报告。

## 交付与回滚

按 P0、P1、P2、P3、P4 分批提交，各批附基线对照、正确性结果和已知兼容范围。先完成低风险冗余消除再推进状态模型变更。缓存格式尽量保持运行时私有；持久化升级须有版本标记和旧存档恢复规则。每项优化提供开发诊断开关或可独立回滚的提交，发现未知附属修改采用保守回退。正式发行遵循仓库固定 Release 流程。
