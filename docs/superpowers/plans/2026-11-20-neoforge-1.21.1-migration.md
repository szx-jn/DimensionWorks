# DimensionWorks 1.21.1 NeoForge 全仓迁移与重构规划书

日期：2026-11-20。工作分支：`1.21.1-neoforge`。调查基线：提交 `8293b522`，根目录 `VERSION=0.3.52`。

本文是实施与验收规划，不代表迁移已经完成。本次交付只新增规划文档及文档索引，不修改游戏代码、Mod 清单、版本号或正式发布流程。

## 1. 目标、结论与执行约束

最终交付一个完整的 **Minecraft 1.21.1 + NeoForge + Java 21** 整合包，保留原有世界、玩家资产、工业体系、多维度职责、跨维度物流、进度、中文资源及客户端/服务器更新能力。运行时彻底移除 Forge 1.20.1 实现；自研代码同时完成有依据的结构整理。

建议采用以下顺序：**先证明核心第三方组合与旧存档转换可行，再迁移底座和自研系统，最后迁移完整内容、更新器与发布链路**。不能先把所有版本号改成 1.21.1，再用删 Mod 和忽略错误的方式勉强启动。

现阶段的重要结论：

1. 分支名称已经就位，但技术迁移尚未开始。相对调查时的 `origin/main`，新增内容全部位于 Remotion 宣传片资源；Mod、清单、脚本和部署实现仍以 Forge 1.20.1 为基线。
2. 第三方依赖大部分有目标版本候选，**有候选不等于组合兼容，更不等于旧存档兼容**。完整逐项调查见[附录：182 项 Mod 迁移矩阵](2026-11-20-neoforge-1.21.1-mod-matrix.md)。
3. 六洞穴、AE2 存储、Mekanism 化学库存、玩家 Curios/背包和三项自维护 fork 是发布前必须解决的重点。不能只验证原版背包与主世界。
4. 现有更新器的文件事务不能回滚新版首次启动对世界的修改。首次跨 Minecraft 版本和加载器升级必须有独立迁移流程。
5. 重构应围绕当前已经存在的重复、职责混杂、存档格式与第三方耦合，不合并所有自研 Mod，不创建巨型公共运行时，不重做已稳定的玩法。

### 1.1 本次明确覆盖的仓库规则

用户已明确要求升级 Minecraft、更换 NeoForge，并要求首次升级保留玩家和服务器旧存档。这项要求优先于当前 `AGENTS.md` 中“1.0.0 前禁止向后兼容”的通用规则。

实施前同步修改该分支的 `AGENTS.md` 技术基线，并为**本次 Forge 1.20.1 → NeoForge 1.21.1 的一次性存档迁移**写明有限例外。例外只覆盖实际旧数据识别、导出、转换、恢复和必要的旧版本导出工具；不扩展为多加载器运行时，也不恢复已删除的所有历史 API。目标代码只实现 NeoForge 1.21.1。

其他规则继续执行：原注册命名空间优先保持；专属物品继续进入 `dimensionworks_cave_factory:main`；新增依赖或更换第三方项目须列出理由再确认；第三方改动通过独立 fork 和固定 GitHub Release；正式产物仍由 Actions 构建与发布。

### 1.2 “保留存档不崩坏”的验收定义

将用户要求拆成可验证的结果：

| 要求 | 必须达到的结果 |
| --- | --- |
| 原档安全 | 转换、下载、启动、验收和切换失败，都不能改写唯一原档；旧实例及冷备份可继续恢复使用 |
| 世界完整 | 所有已有维度与已生成区块能够读取；既有建筑、方块状态、实体及方块实体数据没有未经说明的消失 |
| 玩家完整 | 所有实际玩家 UUID 的背包、末影箱、Curios、背包内部内容、经验、进度、位置及权限归属得到处理，覆盖离线玩家 |
| 工业资产完整 | AE2 存储、Mek 化学/流体、Create 装置、自研物流库存和云盘等按可比口径对账；不得以总物品数量相同掩盖 NBT/组件丢失 |
| 可恢复 | 首次升级失败能恢复完整旧实例；已经在新版产生新进度后，不能声称可无损降级，须明确回退会放弃切换后的变化 |
| 全体覆盖 | 所有实际存在的源版本、登录身份模式和数据格式都有明确迁移路线；不支持的输入明确阻止升级，原档保留，并补齐路线后才纳入成功交付 |

**规划书本身不能证明所有任意历史存档都能无损升级。** 当前未获取生产世界与全部玩家实例，也没有运行目标整包。正式承诺必须建立在实际源版本盘点、注册表对比、转换报告和真实存档副本验收之上。安全中止只能证明没有毁坏原档，不能冒充该存档已经成功迁移。

## 3. 目标技术底座

| 部分 | 目标及处理方式 |
| --- | --- |
| Minecraft/Loader | 精确 1.21.1 和 NeoForge 21.1 系列；选定并锁定单一经过整包验证的版本 |
| Java | 构建、客户端、专服与安装器统一 Java 21；实际启动进程必须使用它，不能只检查 shell 中的 `java` |
| Gradle | 采用官方 1.21.1 MDK 与 ModDevGradle 相互兼容的固定组合，加入 Wrapper；不用本机碰巧安装的 Gradle 版本作为项目契约 |
| 构建依赖 | 在仓库内共享构建约定；自研工程之间改为明确 project/API 依赖，消除读取邻项目陈旧 `build/libs` 的做法 |
| 注册与资源 | 保留现有 modId、物品/方块/方块实体 ID、维度 key 与主要数据文件名；重构 Java 包名不自动改动存档 ID |
| 网络 | 按目标版本迁移到 payload 注册与 StreamCodec；客户端与服务器使用同一协议契约，服务器校验所有会修改状态的请求 |
| 数据 | ItemStack 使用目标 Data Components；世界级数据仍使用 SavedData；实体数据与物品/流体/能量能力按 NeoForge 1.21.1 API 区分 |
| Mixin | 每个注入点对照所选目标依赖源码重新确认；删除已失去必要性的补丁，不将 `require=0` 和吞错作为迁移完成标准 |
| 发行 | 清单锁固定资产及摘要；普通提交不触发正式发布；正式版本号仍由现有发布工作流规则决定 |

Java 21、物品组件和 API 变化可参考 [1.20.5 迁移说明](https://docs.neoforged.net/primer/docs/1.20.5/)。实体数据、物品组件和世界级数据不是同一种存储，应分别依据 [Data Attachments](https://docs.neoforged.net/docs/1.21.1/datastorage/attachments/)、[Data Components](https://docs.neoforged.net/docs/1.21.1/items/datacomponents/) 和 [Saved Data](https://docs.neoforged.net/docs/1.21.1/datastorage/saveddata/) 核对。

### 3.1 构建结构的最小重构

保留现有独立 Mod 的注册边界。先统一重复的 Java 工具链、依赖仓库、资源展开、测试及 mixin 配置，再整理确实存在的源码依赖：

```text
cave-factory ───→ rpm-limit
mek-stress ─────→ rpm-limit
mek-stress ─────→ cave-factory 的配置能力（当前为反射调用）
```

当前没有证据证明自研 Java 依赖已经成环，不以“消除循环”为名重做全部工程。对调用者只暴露已有需求所需的小接口；不把全部业务塞进公共 Mod，不引入加载器抽象层。

## 4. 第三方 Mod 的保留策略

### 4.1 调查状态与锁定方式

附录覆盖清单全部 182 项。候选取自精确版本/加载器过滤的上游元数据或项目页面，并注明来源；调查结果分为“原项目有候选”“需要换来源/自维护移植”“当前来源无候选”“未核实”，不能把缺少搜索结果写成不存在。

### 4.3 六洞穴的社区移植路径

原 Alex's Caves 和维度附属的当前 Modrinth 项目没有精确目标候选，但已发现 [Alex's Caves 非官方端口](https://modrinth.com/project/alexs-caves-%28unofficial-port%29) 和[维度附属非官方端口](https://modrinth.com/mod/dimensions-of-alexs-caves-unofficial-port/)。另有 [AlexsCavesNeo](https://modrinth.com/project/alexscavesneo) 候选来源。它们是审查对象，不是已批准替换。

首个候选页面写的是五种洞穴，但其 [main 分支的 ACBiomeRegistry](https://github.com/Raguto/AlexsCaves-1.21.1/blob/main/src/main/java/com/github/alexmodguy/alexscaves/server/level/biome/ACBiomeRegistry.java) 已明确枚举六种，包括糖果洞穴；不能据旧简介判定缺第六种，也不能把 main 源码当作发布资产的验证。两个端口均有许可证标注冲突，需要对照所选提交和发布资产澄清。调查与样机依次核对：

1. 实际源码/资产中的六种生物群系、方块、实体、战利品和糖果洞穴覆盖。
2. 与原版 Alex's Caves 的注册 ID、方块属性及实体/方块实体 NBT 差异。
3. 维度附属与选定洞穴端口、Citadel 端口的依赖要求和六个维度 key。
4. 原维度已有区块直接读取或显式转换的能力、新区块接缝及资源生态。
5. 许可证、固定资产、上游缺陷及维护成本。

优先选择能够保留全部六洞穴且旧数据可转换的组合。若社区端口缺少关键内容，先评估在独立 fork 中补齐的范围；无法证明核心世界数据安全时，停止正式迁移交付，不能默认删掉洞穴维度。

当前所查维度端口 `1.1.0` 固定依赖 Raguto 的 `2.0.10`，后者要求独立 Citadel 端口；AlexsCavesNeo 则使用官方 Citadel 链。必须按实际版本依赖选整组，不把两个 Alex 端口或两个 Citadel 实现混装，也不假定维度端口可直接配任意 Alex 移植版。

### 4.4 三项自维护 fork 与 ExtendedAE

`Create-Mobile-Packages`、`KaleidoscopeCookery-Automation`、`TrueUUID-DimensionWorks` 的当前固定资产均是旧平台版本。必须分别选择目标上游基线，重新审查本包补丁，再完成 NeoForge 移植、测试和固定 Release。不能只换为未打补丁的同名上游版本。

CMP 重点保留玩家包裹、解包行为、空 Mek 盒掉落修复和弹力工具所依赖的字段。自动料理重点保留已有自动化动作；TrueUUID 重点保留认证与数据归属，不能只以成功进入服务器作为身份迁移验收。

ExtendedAE 需要单独审查目标项目/命名空间与当前 `expatternprovider` 的差异，不能因为同属 ExtendedAE 就假设已放置设备、扩展样板和库存自然继承。

### 4.5 渲染、依赖代际与测试候选

旧 Oculus/Mekalus 实现优先替换为目标 **Iris + Sodium** 渲染链以保留光影；当前 Embeddium 也有目标候选，作为另一整组选择，不能与 Sodium 混装。颜色轮、Iris Shader Folder、SodiumExtras 的依赖和配置随所选渲染链调整，明确写出停止分发旧实现而保留的实际功能。

NeoEcoAE 的所查候选依赖 AE2 和 **LDLib2**，不是旧 LDLib 的直接 API 升级。KubeJS Create/Mekanism 所查候选为 beta；其他候选也可能是 beta，附录保留上游发布类型。这不修改本整合包 `x.x.x` 版本规则，但要求更谨慎的目标配方/存档验收。

所查候选还出现当前清单未列的依赖，例如 Aether 的 owo-lib、KubeJS 的 Better Advanced Tooltips、JEI 的 MezzConfig、Miner's Delight 的 Lodestone，以及所选渲染链的相关组件。它们只列为依赖闭包审查任务，不在本次加入清单；先核嵌入状态、环境和所选版本的实际要求，再说明理由并确认。

## 6. 自研 Mod 的迁移与重构

### 6.1 重构规则

每个模块按“固定旧行为与数据契约 → 移植 API/序列化 → 有边界的职责整理 → 回归验证”推进。不要将一次大规模类移动与行为算法替换放进同一个不可定位的提交。

允许保留已有好用实现。只有观察到职责混杂、重复计算、实际性能问题或存档/API 耦合时才拆分。保留源码工程/注册 ID，避免因重命名“看起来更整洁”额外制造存档转换。

共同处理项：构建约定去重、去除陈旧本地 JAR 依赖、统一日志与错误定位、客户端/专服边界、目标事件/能力 API、组件和 SavedData 编解码、按所选依赖重新审计 mixin。反射仅在确有可选依赖需求且无法用接口解决时保留；有数据损坏证据的错误应进入诊断报告，不静默当空库存。

优先级为：构建与数据契约 → 低耦合模块试迁 → rpm-limit → mek-stress → cave-factory/transfer → 全整包回归。六洞穴依赖可行性在此之前验证。

## 8. 旧存档的数据契约与转换方案

### 8.1 先盘点实际输入

仓库 `VERSION=0.3.52` 不证明服务器和所有玩家都使用这个版本。实施第一阶段先收集实际源包版本、Mod 清单、登录模式、世界大小、维度列表、玩家 UUID 与曾用的重要附属。对旧版本已被删除的注册和数据格式进行扫描后，才能制定支持范围。

不擅自假定“全部先升到最新 Forge 即可”：如果中间版本已经清理兼容并会丢旧数据，先跳到它可能造成损失。需要中间升级时，必须在副本证明完整链路，再写入受支持源版本路线。

没有世界副本时可以完成代码与样机，但旧档正式迁移验收保持未通过。后续确需测试服/脱敏存档时再取得用户提供或授权，不在规划阶段读写生产服务器。

### 8.2 注册与存储映射账本

为每个实际使用的注册项和存储结构建立一份可审查账本：源标识、目标标识、保留/转换/停用状态、转换器、证据、测试样本和数量/归属对账规则。范围包括物品、方块、方块状态属性、实体、方块实体、维度、生物群系、流体、化学品、附属注册项及自研数据。

优先保持 ID。若目标移植更改 ID，必须在目标世界加载前或明确受控的数据修复入口完成映射；不能靠“缺失注册警告后继续”恢复。物品名相同但库存格式不同，也必须列入转换任务。

| 数据位置 | 处理与核对内容 |
| --- | --- |
| `level.dat`、各维度 region/entities/poi、世界生成信息 | 原版升级按正确 DataVersion 处理；模组注册/属性/维度保留另行验证，严禁伪改 DataVersion 冒充转换 |
| 所有 `playerdata` | 每个 UUID 的装备、背包、末影箱、位置、效果、等级及 Forge 持久数据；离线玩家不等待首次登录才发现丢失 |
| Curios、Sophisticated、TLM、其他容器 | 旧能力数据与新组件/附件、嵌套物品、升级件、实体装备及主人 UUID |
| AE2 存储单元/样板/附属 | 存储内容、组件/NBT、容量、编码样板、频道设定；有自定义压缩格式时通过所属 Mod API 导出导入 |
| Mek 方块/机器/容器 | 物品、流体、化学品、升级件、加工中间状态、多方块与频率/安全归属 |
| Create 运动结构、列车与包裹 | 装置内方块实体/库存、移动实体、站点、列车、包裹内物品及玩家包裹；不仅扫描静止箱子 |

| 物质球、自研安瓿、机器库存 | 包装内物品/流体、完整自定义属性、数量和拆包语义 |
| `dimensionworks_transfer_territories.dat` | 领地编号、玩家归属、升级/解锁状态及下一分配序号 |
| `dimensionworks_transfer_returns.dat` | 返回维度、坐标及相关状态；目标维度缺失时阻止激活或明确转换到经确认的安全位置 |
| `dw_dispatch_tutorial.dat` | 教程进度与暂存手持物品；中途处于教程的玩家也要覆盖 |
| `dimensionworks_molten_crystallization.dat` | 世界待结晶状态；避免重复结晶奖励或队列永久丢失 |
| `dw:transfer`、`dw:transfer_void` | 中转维度/生物群系 key 与旧区块，不能改成新命名空间后生成另一张空世界 |
| Create节点的真实机器限额与所有者 | `dimensionworks_machine_rpm_limit`、`dimensionworks_owner`及写入NBT的`DimensionWorksMachineRpmLimit`/`DimensionWorksOwner`保留；派生`DWNetworkRpmLimit`不能替代真实机器限额 |
| Create节点 `DWKineticAccounting` | 含Version/Capacity/Stress/Members/OwnCapacity/OwnStress，涉及未加载物理成员；保持格式并转换，或对完整物理成员重建且证明账目一致，不能只统计已加载节点 |

文件名的保留不等于结构兼容。目标编解码明确区分持久业务数据、含未加载物理成员的保存账目与可重建缓存。资产和约束必须保留；保存账目需要转换或完整重建证明；线程状态和临时同步缓存不原样导入。不能因为某数据名字含network就把它当可丢弃缓存。

三个容易漏掉的具体边界：

- `ChannelStockSavedData` 的物品原型 `Stack.Count` 通常为1，真正库存数量在 `Amount`；对账必须按逻辑库存量而非原型数量。
- 自研驱动/传输方块与方块实体注册名不同，例如方块 `cross_dimension_transmitter_tierN` 对应BE `cross_dimension_transmitter`；按方块ID猜BE会漏转换。
- 安瓿有 `ExpiresAtEpochMs` 的真实时间到期字段。迁移耗时是否继续计算或冻结剩余寿命需要明确规则；不能悄悄补满寿命，也不能让维护流程无说明地销毁全部现有流体。

还应纳入皮蛋待选择/倒计时、旁观返回、玩家正在打包/运输的状态、Gear Heart里程碑/奖励标记、Mek盆内自研化学缓冲，以及方块实体各槽的完整物品特征。不得将所有旧Tag粗暴塞入 `custom_data` 就宣称玩法能读懂它们。

### 8.4 转换路线的取舍

优先使用目标 Mod 已有且经过副本验证的数据修复。对原版类型明确的数据，调用正确的官方升级链；对自研结构使用一次性、版本明确的转换。

对 AE2 单元、Sophisticated 容器等复杂格式，若目标原生迁移不能证明完整，则使用**冻结旧包环境的导出工具 → 带版本的中间数据 → NeoForge 目标导入工具**。旧侧工具只处理迁移，不进入最终整包的常驻运行路径。通过原 Mod API 读取复杂容器，避免自行猜测二进制压缩格式。

必须覆盖全部已生成区块、实体文件、离线玩家、世界数据文件和可识别的嵌套库存；按批次检查点扫描，记录源快照摘要。需要加载旧世界导出时只运行副本，禁用产线和登录，避免导出过程生成新资产。不能只扫描在线玩家或已加载区块。

转换输出带格式版本、源快照标识、完成记录与可重跑检查；重复执行不重复发物品、不叠加奖励、不更换主人。未知格式、缺失注册、未解决的映射冲突或无法对账都停止激活。错误报告列文件/位置/UUID和原因，原始数据留在备份，不能“忽略失败项后成功”。

## 9. 玩家与服务器首次升级流程

### 9.1 共用状态机

```text
盘点实际源版本/身份/资产
  → 停止写入并确认进程退出
  → 完整冷备份、校验、磁盘空间检查
  → 创建独立目标实例，安装 Java 21 / NeoForge / 完整锁定整包
  → 在副本上转换，生成逐项映射与资产对账报告
  → 启动副本并验收，保存、退出、再次启动
  → 验收通过后切换启动入口或服务器服务目录
  → 确认实际运行实例及 VERSION，再宣告迁移完成

任一步失败：目标实例不激活，完整旧实例和原档保留
```

文件系统原子重命名只用于同文件系统适用场景；启动器引用、快捷方式、服务配置和多卷路径也要明确更新。跨卷复制不宣称是原子切换。通过升级日志与完成标记恢复中断事务，不以盲目重试代替定位失败。

完整冷备份包括世界、Mod 固定版本/可恢复安装材料、实际配置、世界外玩家/团队/认证/权限数据、启动参数与 Java/Loader 信息。可再生缓存和无用日志可按明确规则排除；私有数据只留在用户本地/管理员备份中，不进入仓库或公开验收附件。

### 9.2 玩家客户端

1. 验证实际游戏根目录及运行中的客户端已经关闭，识别启动器和来源实例；支持含中文/空格的路径。
2. 备份全部本地单机存档、资源/设置及实际模组玩家数据；只联机的玩家也保留旧实例与设置。
3. 创建新的目标启动配置，安装目标 Minecraft/NeoForge 与 Java 21，安装完整目标整包；不能保留 Forge 启动描述再仅替换 Mods。
4. 在副本迁移每个单机世界；未通过的世界保留旧版启动路线，不在新版入口自动加载它。
5. 迁移按键、资源包和需要保留的个人设置；验证目标 Java、根目录、Loader、Mod 清单和服务器协议匹配。
6. 成功后明确给出新入口及旧实例/备份位置。不能凭目标文件已下载就报告世界成功升级。

客户端与服务端模组/协议不仅按 `VERSION` 大小判断。保留根目录 `VERSION` 为安装版本真相源，另外在受管理目标清单和握手中校验 Minecraft、Loader、协议和必要的资产集合；旧客户端不得因版本号异常进入新服。

### 9.3 服务器

1. 保持当前认证模式、玩家 UUID 和服务端标识；本次迁移不顺便切换 Mojang/MSL/离线身份体系。
2. 维护窗口关闭登录和外部写入，正常保存停服，确认进程退出后做完整冷备份。先在隔离端口的副本完成演练。
3. 在独立目录安装 Java 21、目标 NeoForge 专服和完整整包；配置转换覆盖实际 `world/serverconfig`，同时保留服主自定义。
4. 保留世界种子、全部维度目录、登录与权限数据。副本不接入原生产写入路径，不让两个实例同时写同一世界。
5. 管理员检查所有离线玩家数据报告；用真实客户端验证登录、资产、工业生产、维度往返与权限；执行保存重启回归。
6. 演练通过后，为最终维护窗口重新冻结生产状态并迁移新的冷快照，不能用几天前的演练世界覆盖玩家的新进度。
7. 切换服务入口、端口/反向代理和维护状态；观察约定时间的保存、重启、性能及玩家资产异常，再结束迁移。

回退必须恢复旧程序、完整旧世界、配置与身份/权限数据这一组快照。只换回旧 JAR 或把新版世界复制回 Forge 都不是有效回退。切换后发生严重问题时保持维护，明确告知回退丢弃的新进度范围，不能把新旧世界随意混合。

## 10. 更新器、打包与发布改造

### 10.1 首次跨代不能复用普通增量更新

保留现有文件摘要、路径保护和事务功能，用于同平台常规更新；新增明确的跨代迁移类别。清单需表达源/目标 Minecraft 与 Loader、协议及一次性迁移版本，不让旧客户端把目标包当普通 delta。

当前 `release-pack.yml` 会将任意手动触发分支发布设为全仓共享的 **Latest**，旧更新器默认跟随Latest，跨平台delta基线也未设门禁。因此第一次发布NeoForge必须先解决发布通道与旧更新器行为：桥接版本识别并拒绝跨代，或者目标包使用能令旧解析器安全拒绝的独立入口/格式，并调整Latest与delta选择。仅在Release简介写“先备份”不足以防止自动覆写。

为现有玩家提供能够识别该迁移的更新入口：必要时先发布只有更新器/导出能力的桥接更新，或者提供独立迁移工具。桥接不是强制升级旧世界到某个中间游戏版本。未经检查的旧更新器不得获取一个会直接覆写 Mods 的 NeoForge 更新包。

### 10.2 打包改造

- `package_mrpack.py` 从 Forge 依赖改为正确的 NeoForge dependency，客户端完整安装流程同步更新。
- `package_server.py` 改为 NeoForge 安装器、库目录和实际启动参数；Java 检查验证 21。
- 清单和验证器去掉当前拒绝非 Forge 的约束，改为精确目标平台约束，完整校验内置模组资源与客户端/专服环境。
- `pack_manifest.py` 与 Go 清单解析同步更新跨代字段；新旧清单必须有明确边界和启动路径。
- 保留下载摘要与固定源；`pending-release`、移动分支和临时 Actions 产物不能进入最终整包。
- BBSMC 与其它分发端识别 NeoForge 元数据，校验下载资产和更新器后缀规则，防止旧 Forge 标签污染新版本。

### 10.3 Actions 与版本纪律

调整 Java/Loader、共享构建顺序、目标分支及资产校验时，同步维护正式发布说明输入和拼接逻辑。迁移分支的 `workflow_dispatch` 必须明确构建被验证的目标提交；工作流若按 `main` 硬编码 checkout，先修复再使用。

开发阶段仅做与改动对应的本地检查或必要测试并提交推送；专门的完整存档/客户端验证按迁移阶段执行并保存证据，不设为所有普通提交的昂贵前置。

最终正式发布需要单独明确授权。版本仍为 `x.x.x`，普通发布留空 `release_version` 由工作流递增补丁；升级加载器不自动构成完成维度或提升主版本。Actions 成功后给出固定 Release 资产链接；Actions 成功不代替真实存档验收。

## 11. 验证、性能与准入条件

### 11.1 测试分层

| 层级 | 检查内容 | 何时执行 |
| --- | --- | --- |
| 静态 | diff、清单/JSON/YAML、脚本语法、资源路径、注册引用、平台残留与资产固定性 | 每个相关提交前 |
| 编译/单元 | 模块构建、序列化、算法、组件与新网络契约；复用现有有意义测试 | 模块移植/重构后 |
| 服务器 GameTest | 方块实体、跨模组能力、区块重载、网络分裂合并、玩家状态和迁移样本 | 相关系统迁移后 |
| 新档整包 | 双端启动、脚本、配方链、六维度、登录与资源渲染 | 所选依赖组合和完整内容集就位后 |
| 旧档副本 | 所有源版本路线、资产对账、离线玩家、全维度读写及保存重启 | 正式跨代发布前必须通过 |
| 更新演练 | 全平台、各实际启动器、冷备份、失败中止、切换与整实例恢复 | 更新器就位且正式迁移前 |
| 实际联机 | 真实管理员/玩家账号、权限、操作、日志和长期保存 | 测试服演练与正式维护窗口 |

不能以几次成功启动覆盖数据验证。转换测试应能发现具体资产/归属/组件丢失；不新增只验证语言常识、重复实现或无依据极端输入的测试。

### 11.2 最少需要的代表性旧档

样本按实际服务器/玩家情况选取，不伪造“全覆盖”：

- 所有实际源版本及身份模式；至少一个复杂生产世界，并覆盖与生产完全相同的固定 Mod 集合。
- 在线/离线、死亡重生、曾改名或迁过 UUID 的玩家；装有心脏与背包、持有附属单元/工具的玩家。
- 六洞穴、中转、暮色、Aether、主世界/下界/末地的已生成建筑与长期产线。
- 含组件/NBT、流体、化学品、AE2 单元和样板的嵌套容器；运动 Create 装置、列车和玩家包裹。
- 自研频道、云盘、物质球、教程中途、返回点、待结晶队列和未加载区块。

源数据对账输出按 UUID/维度/容器/频道/物品特征聚合并保留必要定位，不只比较总数。正常模拟造成的合法加工变化与迁移差异分开核查；停机资产核对尽量在开始模拟前完成。

### 11.3 性能约束

旧档扫描/转换是一次性工作，在独立工具或维护阶段按批次执行，不进入每 tick 常驻逻辑。测量磁盘占用、处理时间和峰值内存后确定批次及维护窗口，不先承诺固定几分钟完成。

运行时继续控制区块加载、节点扫描与同步成本：依赖块/能力失效通知更新缓存，已存在的大 Create 网络、跨维频道、女仆和 AE2 设备使用同一场景比较。记录 MSPT 分布、卡顿尖峰、加载区块数、实体/机器数、内存与保存时间。以同配置旧版基线及目标硬件容量判断可接受区间，不用空世界平均 TPS=20 证明大服性能。

基准与实际旧档使用同一锁定目标组合。出现新卡顿先定位来源，再决定是否恢复/改写旧优化补丁；不把所有旧 Create 内部优化无条件照搬到新版本。

### 11.4 一票阻止正式迁移的条件

任一条件存在就不能把“整个整合包迁移完成”作为交付结论：

1. 核心六洞穴或其它已使用维度缺失且没有获确认的安全处理方案。
2. 注册映射不完整、玩家/工业资产对账失败、未知数据被默认清空。
3. 实际玩家源版本或身份模式存在未覆盖的迁移路线。
4. 原档未冷备份、恢复未演练、更新器可能原地覆写唯一世界。
5. 专服启动/脚本/配方/关键联机失败，或者保存重启导致资产/归属变化。
6. 目标依赖未锁定，许可证未清楚，fork 尚无固定可发布资产。
7. 原有生产体系出现未经确认的断链或不可接受的真实负载退化。

## 12. 阶段任务与交付物

| 阶段 | 必做工作 | 完成凭据 | 依赖/停止条件 |
| --- | --- | --- | --- |
| P0 盘点与冻结 | 源包/实际世界/身份/玩家版本盘点；保留基线；注册与存储账本；更新该分支技术说明 | 源版本支持表、内容/数据清单、旧行为样例、备份恢复约定 | 不能把仓库版本当所有玩家版本 |
| P1 核心可行性 | 锁核心候选组合；六洞穴社区端口覆盖；AE2/Mek/背包旧数据样机；三 fork 移植边界 | 固定组合、缺口/风险表、少量真实旧数据转换成功与失败证据 | 核心存档无可行路径就暂停扩张，不先批量移植182项 |
| P2 构建与数据底座 | Java21、NeoForge、Wrapper/共享构建、注册保持、序列化与跨代清单契约 | 低耦合试迁模块构建、专服启动、转换器契约测试 | 使用 P1 选定版本，不频繁追最新 |
| P3 自研重构 | 按第6章模块顺序迁移16工程；优先rpm/mek持久化与能力，再工厂/物流；复用测试 | 各模块 README、构建/测试、数据和行为对比、mixin清单 | 大算法改写与API迁移分提交 |
| P4 内容集成 | 全部第三方资产、KubeJS/配置/资源/世界生成、完整生产链及中文 | 无脚本错误、有效配方/注册报告、全维度新档与副本检查 | 不以删除错误配方掩盖依赖缺口 |
| P5 首次升级工具 | 完整安装、源预检、冷备份、副本转换、目标激活与失败恢复；桥接/独立入口 | 客户端与服务端跨代演练、Windows/macOS/Linux及实际启动器报告 | 无未演练的原地世界修改 |
| P6 完整旧档验收 | 最新冷快照、全玩家/资产对账、全维度读写重启、性能、管理员真实联机 | 迁移报告、差异为零或逐项获确认、恢复记录、阻塞清零 | 安全中止不算成功迁移 |
| P7 正式交付 | 清单固定、发布说明、玩家/管理员手册、Actions正式构建，维护窗口切换 | 固定Release、校验清单、迁移/回退手册、生产观察记录 | 另行正式发布/部署授权；不改VERSION提前发号 |

关键路径是 **核心依赖与数据可行性 → 序列化契约 → 工业/物流迁移 → 全量旧档验收 → 首次更新交付**。文档、配置调查、低耦合模块和工具契约可并行；同一存档格式及依赖锁定由一个明确负责人维护，避免各模块自己发明互不兼容的转换格式。

### 12.1 工作量估算的用法

按可交付任务估算，不承诺无依据的完成日期。P0/P1 的首轮工作用于降低不确定性；P1 通过后再根据选定端口、真实世界规模和三 fork 状况排实施批次。

现有约三万行主 Java 和大量跨模组注入说明这是分阶段工程。目标 API 移植、存档转换和游戏回归的成本不能用改 import 的行数估计。六洞穴端口补齐、认证 fork 和复杂第三方库存转换单独估算；若必须自行移植大型第三方 Mod，它会改变整个工期，应先报告具体范围再决定继续。
